## 1. Research Objective

The objective of this specification is to establish a **research-grade, leakage-free, and methodologically defensible benchmark split policy** for the planned 2,000-core and 300-stress prompt benchmark suite.

In the initial audit report (`reports/benchmark_source_audit.md`), certain heuristic allocations were proposed primarily to satisfy categorical quotas (e.g., drawing benchmark training examples from MMLU source `test` and BBH source `test`). This policy document explicitly reconsiders and corrects those heuristic proposals. 

The goal of this benchmark is to evaluate cost-aware model routing policies across multiple open-weight and proprietary models (initially Qwen 2.5/3 series: 1.7B, 4B, 8B). If benchmark training pools consume canonical source test sets, or if benchmark evaluation sets contain unlabelled competition records or training-leaked prompts, the resulting routing models and evaluation metrics will be methodologically compromised.

---

## 2. Split-Policy Principles

Every allocation in this benchmark must adhere to six inviolable architectural principles:

### Principle 1: Strict Directional Preservation
Where a source dataset provides canonical, labelled splits, the allocation must preserve standard ML evaluation boundaries:
$$\text{source train} \longrightarrow \text{benchmark train}$$
$$\text{source validation} \longrightarrow \text{benchmark validation}$$
$$\text{source test} \longrightarrow \text{benchmark test}$$
Canonical source test sets must **never** be consumed for benchmark training merely because doing so simplifies quota fulfillment.

### Principle 2: Zero Evaluation Contamination
A benchmark evaluation set (`benchmark test` and `benchmark stress`) must measure genuine generalization. If a router or its candidate models are exposed to canonical test prompts during router training, router policy fitting, or feature extraction, reported routing efficiencies will suffer from evaluation contamination.

### Principle 3: Elimination of Unlabelled Competition Splits
Hugging Face datasets created for active competitive benchmarks often withhold ground-truth labels in their `test` splits (e.g., target labels encoded as `-1` or `""`). Under no circumstances may unlabelled source test splits be sampled for labeled benchmark evaluation. Evaluation sets must be drawn strictly from verified, ground-truth-labelled source pools.

### Principle 4: Single Canonical Representation for Overlapping Sources
When two candidate sources contain overlapping or duplicate task instances (e.g., `google/boolq` vs. `aps/super_glue(boolq)`, or `mbpp(full)` vs. `mbpp(sanitized)`), the benchmark must select exactly **one** canonical representation and exclude the other. Duplicate sampling across datasets is prohibited.

### Principle 5: Deterministic Cryptographic Partitioning for Constrained Sources
When a source dataset only provides a single canonical split (e.g., IFEval providing only `train`), any division into train, validation, and test must be performed via deterministic cryptographic hashing of stable identifiers and random seeds. Dynamic, non-reproducible, or unrecorded runtime shuffling is prohibited.

### Principle 6: Total Stress Suite Quarantine
The 300 stress prompts (`held_out: true`) must **never** be generated by perturbing prompts that exist within the 2,000 core benchmark. Stress prompts must be sourced from strictly held-out records or dedicated out-of-distribution source pools.

## 4. Analysis of Source-Test-Only Datasets

Two candidate datasets natively provide **only** a source `test` split:
1. `openai/openai_humaneval` (164 coding tasks)
2. `lukaemon/bbh` (27 tasks $\times$ 250 tasks = 6,750 reasoning prompts)

We evaluate three methodological strategies (A, B, and C) for each dataset:

### 4.1 Evaluation of `openai/openai_humaneval`

- **Strategy A: Reserve HumanEval Strictly for Benchmark Test / Stress (RECOMMENDED)**
  - *Methodological Benefit:* Preserves HumanEval as a pure zero-shot held-out evaluation suite. Zero HumanEval tasks are exposed to router training or policy fitting.
  - *Methodological Risk:* The benchmark training pool for `coding` cannot draw from HumanEval; it must rely entirely on MBPP.
  - *Distribution-Shift Consequence:* HumanEval prompts are function stubs with docstrings inside def statements, whereas MBPP prompts are natural language problem descriptions with assertion tests. This represents a slight task format shift. However, in model router evaluation, testing whether a router trained on MBPP transfers effectively to HumanEval is standard practice and highly desirable.
  - *Reproducibility Implication:* Completely transparent and immune to benchmark contamination criticisms.

- **Strategy B: Partition HumanEval Internally (e.g., 70% Train, 15% Val, 15% Test)**
  - *Methodological Benefit:* Allows both HumanEval and MBPP to exist in all three benchmark splits.
  - *Methodological Risk:* **Unacceptable.** HumanEval is an internationally standardized 164-item evaluation suite. Consuming 114 HumanEval problems for router training would lead to severe external benchmark contamination. Any downstream researcher auditing the router would flag this immediately.
  - *Reproducibility Implication:* Severely damages external credibility.

- **Strategy C: Exclude HumanEval Entirely and Replace with Another Coding Source**
  - *Methodological Benefit:* Eliminates single-split asymmetry.
  - *Methodological Risk:* Sacrifices the single most widely recognized LLM code synthesis benchmark.
  - *Reproducibility Implication:* Unnecessary when Strategy A cleanly resolves the issue.

**HumanEval Policy Decision:** Adopt **Strategy A**. HumanEval is allocated **exclusively to benchmark test** (25 prompts). Zero HumanEval prompts are permitted in benchmark train or validation.

---

### 4.2 Evaluation of `lukaemon/bbh` (BIG-Bench Hard)

BIG-Bench Hard (BBH) contains 27 diverse, multi-step algorithmic reasoning tasks (6,750 total items), but only provides a single `test` split (250 items per task).

- **Strategy A: Reserve BBH Strictly for Benchmark Test and Stress**
  - *Methodological Benefit:* BBH remains completely held out from router training. Router reasoning accuracy is tested on pure unseen algorithmic puzzles.
  - *Methodological Risk:* Because `configs/benchmark.yaml` lists only `bbh` under the `reasoning` category (which requires 300 core prompts: 210 train, 45 val, 45 test), allocating BBH solely to test leaves the benchmark train (210) and validation (45) reasoning pools empty unless a new source dataset is added to `benchmark.yaml`.
  - *Reproducibility Implication:* Requires an immediate configuration change and new adapter for a reasoning training source.

- **Strategy B: Structured Intra-Task Stratified Partitioning (DISCLOSED EXCEPTION)**
  - *Methodological Benefit:* Preserves all 27 rich algorithmic tasks across train, val, and test. By slicing each 250-item task uniformly (e.g., indices 0..174 for train, 175..212 for val, 213..249 for test), task balance is preserved across splits with zero prompt leakage.
  - *Methodological Risk:* The router trains on prompts drawn from the published BBH suite. If the router is later evaluated against public BBH leaderboards, critics could argue that the router was tuned on in-distribution BBH task structures.
  - *Mitigation:* Document the exact partition boundary in the benchmark specification. Ensure that benchmark `test` reasoning prompts are strictly disjoint from benchmark `train` prompts.

- **Strategy C: Replace BBH with Full BIG-Bench or ARC-Challenge for Training**
  - *Methodological Benefit:* Sourcing train reasoning from a canonical training dataset (e.g., ARC-Challenge or GSM8K CoT) maintains clean split boundaries.
  - *Methodological Risk:* Requires changing `configs/benchmark.yaml` and building new dataset adapters.

**BBH Policy Decision:** For the immediate v1 specification without changing `configs/benchmark.yaml`, adopt **Strategy B** under strict cryptographic intra-task slicing (70% train / 15% val / 15% test within each of the 27 tasks). If the research team mandates zero BBH exposure in train, adopt **Strategy C** in a subsequent configuration revision by adding ARC-Challenge / Big-Bench train.

## 5. Specific Resolutions for Audit Findings

### 5.1 MMLU Source-Split Policy: Correcting the Audit Proposal
- **Audit Proposal:** Sourced 280 training prompts from MMLU `test`.
- **Policy Correction:** Sourcing training data from MMLU `test` violates Principle 1 and Principle 2. MMLU `test` is the global standard for LLM knowledge benchmarking.
- **Defensible Strategy:** `cais/mmlu` provides a dedicated, official `validation` split containing **1,531 curated, labelled questions across all 57 subjects** (~26 questions per subject).
  - Benchmark `train` (280 prompts) $\longleftarrow$ sampled from MMLU `validation` (slice A: ~5 questions per subject).
  - Benchmark `val` (60 prompts) $\longleftarrow$ sampled from MMLU `validation` (slice B: ~1 question per subject).
  - Benchmark `test` (60 prompts) $\longleftarrow$ sampled from MMLU `test` (14,042 available; ~1 question per subject).
- **Result:** **Zero MMLU source test prompts enter benchmark train.** Canonical directionality is 100% preserved.

### 5.2 IFEval Single-Split Policy
- `google/IFEval` contains 541 prompts, all packaged in a single `train` split.
- **Policy:** IFEval must be partitioned into three disjoint subsets using a deterministic hash on the native integer `key`:
  $$h(\text{key}) = \text{SHA256}(\text{"ifeval:"} + \text{str}(\text{key}) + \text{":"} + \text{str}(\text{seed})) \pmod{100}$$
  - $\text{Train (70\%, 175 prompts)}: h(\text{key}) < 70$
  - $\text{Val (15\%, 37 prompts)}: 70 \le h(\text{key}) < 85$
  - $\text{Test (15\%, 38 prompts)}: h(\text{key}) \ge 85$
- **Result:** Verifiable, leak-free partition with zero runtime variance.

### 5.3 BoolQ Duplication Policy
- The audit proved that `google/boolq` and `aps/super_glue` config `boolq` contain identical data row-for-row.
- **Policy:** The `boolq` configuration within `aps/super_glue` is **permanently blacklisted**.
- All BoolQ instances must originate strictly from `google/boolq`.
- All `super_glue` instances must originate strictly from the remaining non-BoolQ tasks (`cb`, `copa`, `rte`, `wic`, `wsc`, `multirc`, `record`).

### 5.4 MBPP Configuration Choice
- MBPP provides two configurations: `full` (974 tasks) and `sanitized` (427 tasks).
- `sanitized` consists of manually reviewed, bug-free problems with verified unit tests. However, its `train` split contains only 120 problems, which cannot satisfy the required 210 benchmark coding train prompts alone.
- **Policy:**
  - Standardize on **`google-research-datasets/mbpp` (`full`)** for the primary source pool, applying automated schema validation to discard malformed test asserts.
  - Alternatively, if `sanitized` is preferred for quality, the 210 train prompts must be drawn from `full` train (374 items) while ensuring that any task ID present in the test pool is quarantined.
  - To eliminate confusion: Core benchmark construction will use **`google-research-datasets/mbpp` (`full`)** with strict deduplication against any task ID assigned to benchmark test.

### 5.5 SuperGLUE and HellaSwag Unlabelled Test Handling
- Both `aps/super_glue` and `Rowan/hellaswag` have public competition `test` splits where ground truth is withheld (`-1` or `""`).
- **Policy:** Ingestion of source `test` for SuperGLUE and HellaSwag is **strictly forbidden**.
- Source `train` supplies benchmark `train`.
- Source `validation` supplies benchmark `validation` and benchmark `test` via deterministic 50/50 disjoint slicing (e.g., first half of val to benchmark val, second half to benchmark test).
- Because SuperGLUE `validation` contains 19,233 items and HellaSwag `validation` contains 10,042 items, there is ample margin for statistically robust, fully labelled evaluation pools.

## 8. Leakage Policy

The benchmark construction pipeline must enforce three strict anti-leakage barriers:

1. **Source ID Quarantine:** Every sampled example retains its native `source_id` (or generated unique provenance key) and `source_dataset`. Before final split assignment, an assertion must verify:
   $$\text{Set}(\text{train.source\_ids}) \cap \text{Set}(\text{val.source\_ids}) = \emptyset$$
   $$\text{Set}(\text{train.source\_ids}) \cap \text{Set}(\text{test.source\_ids}) = \emptyset$$
   $$\text{Set}(\text{val.source\_ids}) \cap \text{Set}(\text{test.source\_ids}) = \emptyset$$

2. **Semantic Text Hashing Guard:** In datasets that contain reading passages shared across multiple questions (e.g., BoolQ, MultiRC, CNN/DailyMail), questions sharing the exact same context text must be forced into the same benchmark split (`leakage_guard: true`). If a passage appears in `train`, none of its sibling questions may appear in `val` or `test`.

3. **Prompt Deduplication Guard:** Exact normalized string matching (lowercase, whitespace-stripped) will run across the aggregated benchmark candidate pool. Any duplicate prompt found across datasets will be discarded prior to split partitioning.

## 9. Stress / OOD Suite Source Policy

The 300 stress prompts (`held_out: true`) test router resilience under adverse conditions. They are allocated as follows:

| Stress Type | Target Count | Dedicated Sourcing Strategy | Overlap with Core Allowed? | OOD vs. Perturbation |
|---|---|---|---|---|
| `long_prompts` | 60 | Sample from unselected CNN/DailyMail articles with token length $\ge 1,500$ tokens. | **STRICT NO** (Must use unselected article IDs) | **Perturbation** (High token volume) |
| `distractors` | 50 | Inject synthetic irrelevant text into unselected MMLU or BoolQ prompts. | **STRICT NO** (Derived from unselected pool) | **Perturbation** (Noise robustness) |
| `paraphrased` | 50 | Paraphrase unselected GSM8K or MMLU prompts using standard rephrasing templates. | **STRICT NO** (Never paraphrase core prompts) | **Perturbation** (Syntactic shift) |
| `formatting_variations` | 40 | Wrap unselected BBH or IFEval prompts into strict JSON/YAML output schemas. | **STRICT NO** (Derived from unselected pool) | **Perturbation** (Schema shift) |
| `harder_reasoning_math` | 40 | Sample strictly from Hendrycks MATH **Level 5** competition problems. | **STRICT NO** (Unselected Level 5 problems) | **Domain Shift** (Extreme difficulty) |
| `code_variations` | 30 | Apply semantic variable renaming and signature refactoring to unselected MBPP tasks. | **STRICT NO** (Unselected task IDs) | **Perturbation** (Code style variation) |
| `held_out_domain_task` | 30 | Reserve 2 complete BBH tasks (e.g., `dyck_languages`, `web_of_lies`) or SuperGLUE `wsc` exclusively for this stress set. | **STRICT NO** (Entire task excluded from core) | **True OOD** (Unseen task distribution) |

### Provenance Tracking for Transformed Stress Records
When a stress prompt is generated via perturbation (e.g., distractor injection or paraphrasing), its provenance metadata must record:
- `source_dataset`: The original source.
- `source_id`: The original source record ID.
- `stress_transformation`: Explicit label (e.g., `"distractor_injection_v1"`).
- `prompt_id`: A distinct prefixed identifier (e.g., `stress_distractor_001`).

## 10. Deterministic Sampling Implementation Requirements

To guarantee that benchmark generation is 100% reproducible across developer environments and operating systems, the sampling pipeline must implement the following requirements:

1. **Fixed PRNG Seed:** All random operations must use `seed = 42` from `configs/benchmark.yaml`.
2. **Stable Pre-Sampling Ordering:** Prior to sampling, all records within a dataset partition must be sorted lexicographically by a stable compound key:
   $$\text{sort\_key} = (\text{source\_config}, \text{source\_split}, \text{source\_id\_or\_index})$$
   This prevents OS-dependent or Hugging Face cache-dependent dictionary iteration differences.
3. **Synthetic ID Generation for Positional Sources:** For sources lacking native string/integer IDs (`cais/mmlu`, `openai/gsm8k`, `google/boolq`, `lukaemon/bbh`), adapters must generate deterministic, zero-padded provenance IDs:
   $$\text{source\_id} = \text{f"{source\_dataset}\_{source\_config}\_{source\_split}\_{index:06d}"}$$
4. **Deterministic Strata Allocation:** Stratification across MMLU's 57 subjects and BBH's 27 tasks must use integer quotient sampling ($N_{\text{total}} // K_{\text{strata}}$) with residual items distributed deterministically by alphabetical task order.

## 12. Conclusion & Verification

This split policy specification resolves every structural, leakage, and methodological issue identified in `reports/benchmark_source_audit.md`. It guarantees that:
- Core split counts (1,400 train, 300 validation, 300 test) are preserved.
- Canonical source test sets are never plundered for training data.
- Unlabelled competition test splits are eliminated from evaluation.
- Overlapping and duplicate data sources are cleanly resolved.
- Full mathematical determinism and provenance integrity are maintained.
